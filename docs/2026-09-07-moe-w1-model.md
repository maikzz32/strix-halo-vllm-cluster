# W1 full-model trial: small effect, not promoted

The BN32/two-warp W1 candidate preserves all tested model outputs but does not deliver a substantial single-answer improvement. The original W1 kernel remains active with the canonical TP4/UMA configuration.

## Bracketed ShareGPT48 result

Same checkpoint, INT4 asymmetric GS32 weights, BF16 arithmetic, MTP3, context262144, C1 and seed42. Only the opt-in W1 tile selection changes for M4/top10/N320/K2560/GS32/BM16. Prefill, draft and other shapes retain the existing selection.

| Run | Output tokens/s | Mean TPOT (ms) | Mean TTFT (ms) |
|---|---:|---:|---:|
| Original before | 51.17825 | 17.36626 | 542.159 |
| W1 candidate | 52.37690 | 16.95846 | 544.364 |
| Original after | 52.03333 | 17.05490 | 548.828 |

All three runs complete48 requests with14767 input and11839 output tokens. All48 answer texts, per-request input/output lengths and MTP statistics match exactly. Acceptance is54.1427%, with4514 drafts,13542 draft tokens and7332 accepted tokens.

Against the initial control the candidate appears 2.34% faster overall and2.40% faster in generation. Against the stronger final control those differences shrink to **0.66% overall and0.57% generation**. The original controls themselves differ by approximately1.7% overall. These runs support at most a small effect; they do not establish a stable multi-percent model gain.

Six paired512-token streams after the candidate and after restoration use identical requests, including `ignore_eos=true`. All content, reasoning and usage match. Their median paired generation difference is just **+0.17%** for the candidate. Historical pre-trial streams used `ignore_eos=false`; although their outputs match too, they are not represented as identical-request timing controls.

## Deployment and restoration

`tools/patch_moe_w1.py` verifies the complete installed fused-MoE source SHA256 before adding a default-disabled `STRIX_MOE_W1_BN32` shape guard. It changes BN64/four warps to BN32/two warps while preserving SPLITK4/BK128/stages2 and the kernel arithmetic. CPU checks cover the enabled shape, disabled setting, unsupported shapes and rejection of already modified source.

`tools/deploy_moe_w1.py` stages both original and candidate files under `/opt/strix-halo-next/moe-w1-bn32-20260907-r1`; activation/restoration refuse live serving workers and unexpected source hashes. It defaults to dry run. Staging in a separate checkout requires `--base-source` pointing to the reviewed original source. The separate candidate config is in [records](../bench/records/w1-candidate-20260907.json).

The candidate ran as `c0f1317d3f5f4e909b2f9542cff47f43`. All four workers had the candidate and UMA flags active, and all four UMA startup proofs passed32 fresh banks against active PyNccl in eager and graph modes. After its tests, every owned serving process was stopped cleanly and the original fused-MoE source SHA256 `4f460bcc4c6c074dc8c08c3881bccdbdbd941490821bac458c9782c1404a0070` was restored on all four nodes.

The canonical configuration was never overwritten. The restored run `e0844d1a3f2c4988a7513cddb6c946c3` reached READY, passed fresh UMA parity on every rank, then completed the final48-request control and six streams. Final request gauges are idle. No experimental process remains.

[Results, hashes and parity evidence](../bench/records/2026-09-07-moe-w1-model.json) omit generated answer text. Raw logs and replies remain in the workspace. `tools/summarize_moe_w1_trial.py` reproduces the comparison from the three raw benchmark JSON files.

This patch remains available for a combined future experiment but is not enabled in production. The requested substantially higher single-answer speed remains unachieved.
