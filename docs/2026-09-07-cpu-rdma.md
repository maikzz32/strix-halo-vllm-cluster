# CPU-RDMA all-reduce experiment, 2026-09-07

The four-rank host-memory verbs prototype achieves **41.38 µs with FP32 accumulation** and **48.62 µs with BF16 rounding after every addition**, for exactly 10,240 BF16 input values per rank. These are measured CPU collective times, not model throughput or an integrated GPU-graph backend. Production continues to use RCCL.

| Implementation | FP32 then final BF16 | BF16 after each addition |
|---|---:|---:|
| Initial portable scalar C, 256 iterations | 66.128 µs | 115.066 µs |
| Exact AVX2, 256 iterations | **41.379 µs** | **48.618 µs** |

Each entry is the maximum of four rank medians, after 32 warmups. No algorithm/protocol sweep was performed. The initial scalar source and improved source are identified independently in the [compact evidence record](../bench/records/2026-09-07-cpu-rdma.json).

Transport timing includes posting, CQ polling and rank-arrival skew; it is not NIC-only wire latency. Total timing includes local arithmetic, excludes reference checking, and has no GPU producer/copy/callback/consumer costs. FP32 p95 was 43.17–44.03 µs; BF16 p95 was 60.49–60.73 µs. Wall time including output checking was approximately 41.9/51.2 µs.

The old GCC optimization report explicitly rejected vectorization of the arithmetic loop; disassembly contained a call to `reduce_four` for each element and scalar `addss`. The new target-specific helper uses eight AVX2 lanes, preserving rank order and integer round-to-nearest/ties-to-even BF16 conversion. Standalone per-host arithmetic timing fell from 20.0–26.1 to 3.4–4.6 µs for FP32 and from 52.5–68.9 to 8.7–11.1 µs for repeated BF16 rounding. No fast-math or assumption that all inputs are finite is used. Source NaN/Infinity blocks and scalar tails call the shared scalar function; it is deliberately not inlined so NaN operand/sign selection stays identical. Finite overflow and subnormal/zero behavior are checked too. Unsupported CPUs retain the scalar implementation; explicitly requesting AVX2 for networking requires CPU support.

The collective uses three simultaneous RC `RDMA_WRITE_WITH_IMM` sends per rank followed by a local fixed-rank-order sum. **It is full allgather, not ring.** Each rank transmits 3×20,480 = 61,440 payload bytes, excluding protocol overhead. Both accumulation modes send BF16, not FP32. A conventional four-rank reduce-scatter/allgather ring would transmit 30 KiB per rank over six dependent phases; no CPU ring implementation was tested here. Ordinary host allocations are registered once through verbs. There is no MPI/UCX/Torch/HIP/GPU-direct dependency or TCP data fallback.

Correctness uses 32 rotating finite nonzero input banks with cancellation cases, checking every output of every warmup/measured iteration. C/Python fingerprints match. Before the final network run, each host additionally passed bitwise scalar/AVX2 comparison over all banks, eight sets of 65,536 raw BF16 patterns, exceptional values, unaligned pointers and tails. Nine local stdlib tests pass. Both FP32 and repeated-BF16 modes specify their own rounding order; neither claims bitwise identity with RCCL's different reduction tree.

The smoke, scalar measurement and AVX2 measurement all completed: **12 native ranks and launchers exited 0**, native teardown succeeded, temporary remote builds were removed and all 12 final run-ID scans found no remaining rank process. Each rank has a bounded deadline, checked receive epochs, two alternating receive slots, completion validation and owned-process termination. No serving configuration or installed package changed. GPU/network leases were returned after measurement.

To reproduce preparation locally:

```sh
python -m unittest discover -s tests -p 'test_cpu_rdma*.py' -v
python tools/run_cpu_rdma_allreduce.py --implementation avx2 --iterations 256 --warmup 32 --mode both
```

The second command is a dry run. During a separately reserved network-test window, add `--execute --output results/<new-directory>`. It compiles on the four existing Fedora hosts using installed GCC/libibverbs, performs scalar/SIMD CPU checks before networking, then retains local logs, exact expanded source, hashes, status and final process scans. Existing hosts/HCA names and SSH access as `cluster-user` are prerequisites. The `cpu_rdma_reduce_avx2.h` file must remain beside the C source; the driver embeds it into the hashed source sent to each host. No installation occurs.

For CPU-only C checks without verbs on a Linux machine: compile `tools/cpu_rdma_allreduce.c` using `cc -O3 -std=c11 -Wall -Wextra -Werror -DCPU_ONLY -o /tmp/cpu-rdma-reference -lm`, then run that binary with `--self-test` and `--sum-self-test`.

The approximately 85.27 µs RCCL graph baseline and separate approximately 16 µs HIP host-callback/copy baseline motivate a coupled experiment, but adding independent timings is not proof of end-to-end gain. Before a runtime change, a minimal four-rank HIP graph must validate and measure the exact pinned allocation/MR registration, GPU→host readiness, callback collective, host→GPU visibility and repeated graph replay with nonzero numerical checks. The supplied C program remains an experimental benchmark, not a serving plugin or public backend ABI.
