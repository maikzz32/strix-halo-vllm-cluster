# UCCL review for the four Strix Halo nodes

Inspected upstream commit `79b64ae7ca58ea78bb39c6275b0f91443e33a3f2` from a local shallow checkout, following the user's repository link. No UCCL build, installation or service switch has occurred.

UCCL is relevant as an alternative RCCL network transport. Its RDMA collective component supports AMD GPUs and RoCE, and the current code contains explicit Intel/irdma adaptations despite the top-level support summary mainly naming Nvidia and Broadcom NICs. That makes it a concrete test candidate; it does not prove gfx1151 compatibility or better single-answer throughput.

## Source findings

* [Intel settings](https://github.com/uccl-project/uccl/blob/79b64ae7ca58ea78bb39c6275b0f91443e33a3f2/collective/rdma/transport_config.h): `INTEL_RDMA_NIC` changes the traffic-class encoding and disables CQ moderation/ignore-overrun options. [Credit handling](https://github.com/uccl-project/uccl/blob/79b64ae7ca58ea78bb39c6275b0f91443e33a3f2/collective/rdma/transport.cc#L2906) also has an irdma-specific completion-opcode branch.
* [CUDA Makefile](https://github.com/uccl-project/uccl/blob/79b64ae7ca58ea78bb39c6275b0f91443e33a3f2/collective/rdma/Makefile) maps `USE_INTEL_RDMA_NIC=1` to `-DINTEL_RDMA_NIC`. [Makefile.rocm](https://github.com/uccl-project/uccl/blob/79b64ae7ca58ea78bb39c6275b0f91443e33a3f2/collective/rdma/Makefile.rocm) lacks that mapping. [build_inner.sh](https://github.com/uccl-project/uccl/blob/79b64ae7ca58ea78bb39c6275b0f91443e33a3f2/build_inner.sh#L68) forwards the option to the CUDA invocation, but its ROCm invocation does not do so. A ROCm build needs the macro supplied explicitly or the Makefile wiring corrected; the top-level option alone is insufficient in these inspected files.
* [Plugin memory support](https://github.com/uccl-project/uccl/blob/79b64ae7ca58ea78bb39c6275b0f91443e33a3f2/collective/rdma/nccl_plugin.cc#L230) starts with host pointers, adds GDR/DMA-BUF capabilities when detected, and contains a debug assertion if host pointers are the only capability. [Debug macros](https://github.com/uccl-project/uccl/blob/79b64ae7ca58ea78bb39c6275b0f91443e33a3f2/include/util/debug.h#L217) make the assertion conditional on `NDEBUG`. Therefore the required non-GDR path needs a real test; simply observing `NCCL_PTR_HOST` is insufficient proof that our configuration works. Do not merely suppress the assertion and assume correctness.
* [RC/UC selection](https://github.com/uccl-project/uccl/blob/79b64ae7ca58ea78bb39c6275b0f91443e33a3f2/collective/rdma/rdma_io.h#L715) automatically chooses RC when UC is unavailable and supports `UCCL_RCMODE=1`. Its defaults include four engines and 32 paths per engine. These defaults need evaluation for one 25G port and tiny decode messages; a multipath datacenter benchmark is not a prediction for a single-switch cluster.
* [Integration](https://github.com/uccl-project/uccl/blob/79b64ae7ca58ea78bb39c6275b0f91443e33a3f2/README.md): RCCL loads `librccl-net-uccl.so` via `NCCL_NET_PLUGIN`. The inspected plugin exports the v8 network interface. Compatibility with the installed RCCL must be confirmed by actual plugin loading. Our existing UMA path directly handles the frequent 20 KiB target all-reduces, so merely adding the plugin to that configuration would not test UCCL for those operations.

## Appropriate comparison

Keep the installed vLLM, checkpoint and weights. First build a separate plugin with Intel support and verify dependencies/ABI without replacing RCCL or containers. Then use isolated four-rank tests for the actual 20 KiB BF16 payload, including changed-input graph replay and numerical comparison with active RCCL. Compare stock RCCL, RCCL with UCCL, and our current direct UMA path. Explicitly record host staging, RC mode, selected HCA/GID and loaded plugin identity.

Only after those pass should a full-model trial disable the direct UMA override for the UCCL arm. Identical weights alone do not guarantee bitwise equality if the collective algorithm changes; preserve and compare answer texts, token lengths and MTP statistics. EP and KV-cache-transfer features are separate from the current TP4 single-answer workload and are not evidence of faster decoding here.

A fresh original-kernel ShareGPT48 run completed successfully while UCCL was inspected. The original TP4/UMA service remains active; W2 and UCCL have not been activated together or separately in this round.
