# Direct GPU/UMA exchange with four-node CPU RDMA

A separate backend replaces the two HIP copies and host callback with one GPU
kernel. It writes the input into a GPU-mapped, verbs-registered host arena,
publishes a system-scope release doorbell, waits for the CPU verbs thread, then
reads the ordered BF16 sum directly from the arena into the distinct output.
The existing Intel-RoCE transport and calibrated four-ring arithmetic are reused.
The opt-in serving hook now selects this backend for the validated TP4/20-KiB
collectives. Model weights and model arithmetic settings remain unchanged.

| Isolated implementation | Max rank median HIP time, 20 KiB |
|---|---:|
| Earlier copy/callback backend | 56.42 µs |
| Direct UMA kernel, 256 threads | 73.26 µs |
| Direct UMA kernel, 1024 threads | **53.93 µs** |

The 1024-thread wall-clock equivalent is 53.96 µs. Each longer run uses 32
distinct outputs per graph, four changing-input warmups and three samples of
32 graph replays. Every rank passed the existing fresh 32-bank parity checks
against its actual PyNccl communicator, both eager and captured. Input
preservation, output checks, cleanup and unchanged model request counters passed.
These isolated collective measurements are separate from the full-model
comparison below. The earlier callback backend had no full-model gain.

Graph replay correctness is addressed by a GPU-owned 64-bit epoch counter.
The host does not bake an enqueue-time sequence into the graph. A system-scope
active flag rejects overlapping kernels; all ranks must still issue collectives
in the same serialized order. Native progress errors terminate the owning test
worker. Resource teardown synchronizes the GPU, joins the progress thread and
destroys the transport before freeing the borrowed arena. Graph objects must
be destroyed before explicit backend teardown.

Before coupling to RDMA, a standalone Node18 handshake completed 3,204 epochs
and checked 32,808,960 input values. The first four elements encode the full
epoch, preventing periodic input-pattern aliases. Its graph contained only 32
kernel nodes. Injecting a CPU failure left the GPU output canary untouched.
Its 16.77 µs median includes synthetic pattern generation and CPU validation;
it is not a matched comparison with a model copy operation.

The first coupled build failed before GPU execution because hipcc treated the
C object file as HIP source. Compiling HIP and C separately and linking their
objects resolved it. The successful smoke and both longer runs are retained in
the [evidence record](../bench/records/2026-09-07-hip-uma.json).

Reproduce with the existing preserved containers and an idle model service:

```sh
python tools/run_hip_rdma_graph.py --backend-test --uma-backend --uma-threads 1024 --mode ring4
```

The command is a local dry run; add `--execute --output results/uma-new` for the
bounded four-rank experiment. `tools/hip_uma_backend.hip` exposes the same C ABI
as the older prototype and uses the existing mandatory Python parity validator.
The prototype currently spins a CPU progress thread while alive. Full-model
tests passed, but it has not been qualified for unattended service.

The architecture was motivated by the [ds4-vLLm source review](github-vllm-projects-20260907.md).
The implementation here uses the existing four-rank RoCE C transport and adds
GPU-owned replay epochs; it does not install that project's TP2/native-IB backend.

## Full-model comparison and deployment

All three runs use the same ShareGPT seed42, 48 requests, concurrency1,
14767 input tokens and 11839 output tokens, unchanged INT4 weights and MTP3.

| Runtime in test order | Output tokens/s | Mean TPOT (ms) | Mean TTFT (ms) |
|---|---:|---:|---:|
| Existing QSA/RCCL before | 48.5217 | 18.3984 | 543.321 |
| UMA, 1024 threads | **51.7853** | **17.0900** | 544.389 |
| Restored QSA/RCCL after | 50.4409 | 17.6429 | 547.795 |

All 48 generated texts, input/output lengths and speculation statistics match
exactly across these runs. Relative to the stronger, restored control, UMA
improves overall output throughput by **2.665%** and decode speed inferred
from mean TPOT by **3.235%**. The baseline drift prevents attributing the full
6.73% improvement over the first control to UMA. This is a small improvement;
the user's substantially faster single-answer target remains unmet.

Six matched 512-token streaming requests also produced identical answers.
Their median paired decode improvement is 4.12% over the restored control.
One candidate analysis answer contained a 385ms SSE gap and was retained;
its repeat did not show that gap. Six concurrency2/128-token smoke requests
completed, without claiming a concurrency2 speedup.

The first model start passed communicator parity but exceeded the controller's
420-second loading deadline; the controller explicitly cleaned up all ranks.
The retry with a 900-second limit reached READY and produced the measurements.
Do not confuse a polling timeout with confirmation that workers stopped.

The preserved installation uses
`/opt/strix-halo-next/hip-uma-ring4-20260907-r1` in each container.
`tools/deploy_hip_rdma_experiment.py activate --backend uma --execute` selects
the reviewed hook; this does not restart the service. Staging requires the
reviewed original communicator via `--base-source` and an unused addon path.
The candidate configuration is archived alongside this document as
[`hip-uma-model-r1.json`](../bench/records/hip-uma-model-r1.json).
It references that addon through `STRIX_HIP_RDMA_LIBRARY` and `PYTHONPATH`.
These paths require the preserved patched runtime described in the native runbook.

The canonical configuration on all four hosts was promoted to the tested
candidate. Each original is saved as
`/home/maik/strix-halo-next/config/cluster.pre-uma-20260907.json`.
To revert: stop the owned cluster using its current configuration, run the
hash-guarded deploy tool with `restore --backend uma --execute`, restore that
backup to `cluster.json` on all four hosts, then start from the Linux head with
`--timeout 900`. Do not replace running-worker files and assume their loaded
code changed. This remains manual operation without a crash supervisor.

[Full-model evidence and response hashes](../bench/records/2026-09-07-hip-uma-model.json)
retain the baseline bracket. Full response texts and model weights stay outside
Git. The promoted-instance verification is included in the same record.

## Promoted-instance verification

Run `c8ef52cece0841e1b975ff8dd76d1602` reached READY using canonical
`cluster.json` on all four hosts and remained running after validation.
A second complete ShareGPT48 test measured **52.0387 output tokens/s**,
**17.0053ms mean TPOT** and 552.796ms mean TTFT. It completed all48 requests,
with exactly the same texts, lengths and speculation statistics as the RCCL
control. This is +3.168% overall throughput and +3.750% decode speed versus
the restored control. The two UMA model runs therefore show a small,
repeatable average gain rather than the requested large speedup.

The six final matched streams were also identical, with a median paired
+4.918% decode improvement. The first analysis reply included two SSE gaps
of 398.125ms and 364.691ms; its repeat's maximum gap was45.897ms. These events
are retained and remain unexplained. Average throughput does not establish
uniform latency or unattended-service reliability.
