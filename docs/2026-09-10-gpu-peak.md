# GPU profile_peak: rejected

The bounded high/profile_peak/high experiment regressed single-stream decode
by a median paired 8.47% relative to the mean of each request's two controls.
All four nodes were restored to the promoted `high` mode and readback verified.
No model restart or source change was required.

| Median of six fixed-prompt streams | High before | Profile peak | High restored |
|---|---:|---:|---:|
| Decode tokens/s | 72.261 | 66.153 | 72.194 |
| TTFT, seconds | 0.355 | 0.536 | 0.375 |
| End-to-end tokens/s | 65.871 | 58.177 | 65.585 |

Each phase used three prompts with two repeats, 256 output tokens and C1,
following three 32-token warmups. All request bodies, usage, content and
reasoning matched exactly. This is a short diagnostic workload, not the
ShareGPT48 goal metric. The clear negative result does not justify another
full serving trial; the latest promoted ShareGPT result remains 56.364 tokens/s.

The Linux documentation describes profiling modes as disabling clock/power
gating, with `profile_peak` selecting the highest clock levels. That description
does not imply better application performance on this APU. We did not measure
clock residency, CPU frequency or power during this candidate, so the regression
is not attributed to throttling, CPU/GPU power competition or a specific clock.
[Linux amdgpu documentation](https://docs.kernel.org/gpu/amdgpu/thermal.html).

`tools/bench_gpu_peak.py` reproduces the bounded test with a try/finally
restoration on all attempted nodes. It requires the starting mode to be high.
Records `2026-09-10-gpu-peak-{comparison,original,applied,restore}.json` under
`bench/records/` retain parity, timings, raw-result hashes and state verification.
