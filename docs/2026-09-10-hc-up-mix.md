# HC-up projection and gate-mix fusion

The fixed-M4 native candidate passed isolated checks. Its first serving
integration did not reach the compiled decode graph; the dynamic-dispatch
correction reached the full graph but failed full-model output parity. It is
not promoted. No model-level gain has been established.

Original dot-product reduction, BF16 gate rounding, four-stream FP32 FMA order
and final BF16 conversion are retained. A 65,536-entry FP32 lookup table (256
KiB) is generated using the installed Triton sigmoid. A separate finite-BF16
probe found 668 FP32 differences with HIP expf/division; that prototype failed
expanded output parity and was rejected. Eight lanes distribute the epilogue.

## Remaining requirements

The native ABI assumes BF16 weights [10240,320], input [4,320], residual
[4,10240] and output [4,2560]. It does not check a null table pointer. The
serving adapter must enforce valid shapes/pointers, initialize and retain the
table outside graph capture, register a custom operation/fake implementation,
and preserve unsupported-shape and MTP fallbacks.

Actual dispatch/capture validation, ShareGPT48/C1, Hermes and output parity
with matched controls remain outstanding. Prior HC geometry and W1/SiLU fusion
microbenchmarks did not deliver serving gains; this candidate is not promoted.


## Initial integration test

The default-off, hash-guarded source transformer replaces the adjacent pair in
both actual `GatedResidual.mix` and `combine_and_mix`. The runtime initializes
a shared per-device sigmoid table before capture, holds it as a non-persistent
buffer, and registers a custom operation with descriptor checks and a fake
implementation. Target prefixes and unquantized BF16 weights are required.
MTP prefixes and unsupported row counts retain the original path.

Node 4's bounded isolated integration test passed 32 exact-output cases: both
actual HC methods, combined/separate down projections, target/MTP prefixes,
and row counts 1/3/4/5. The test uses synthetic projection modules and explicitly
calls preparation; **it does not exercise the real vLLM layer constructor or
checkpoint loader**. The pair compiles with `torch.compile(fullgraph=True)`
using a graph-inspecting eager backend, which confirms the new custom operator
is present. Changed-input HIP graph replay also matches exactly. This is not
an Inductor or full-model compilation result. Serving counters were unchanged.

See `patches/hc_up_mix_{source,runtime}.py`,
`tests/check_hc_up_mix_integration.py` and the corresponding controller/record.
Real constructor/device initialization, model capture and matched serving
validation remain required before promotion. Production sources are unchanged.


## Real constructor and Inductor validation

All four nodes subsequently passed the real GatedResidual constructor with
vLLM Linear modules, synthetic initialized BF16 parameters, a private singleton
Gloo group, and an explicit default vLLM configuration context. The non-persistent
table is absent from state_dict. The same 32 cases per node pass exactly; both
full HC methods at M4 compile with Inductor/fullgraph and match the original
methods. Changed-input HIP graph replay of the Inductor-compiled pair is exact.
These tests still do not load checkpoint weights or exercise the complete TP4
model. Initial harness failures (missing config context and unregistered test
module) were corrected without modifying the serving runtime.

A TP4/MTP3 serving trial has now started with unchanged checkpoint/configuration
except the opt-in HC pair patch and its Python module search path. Results and
promotion are pending; do not treat startup as a serving performance result.


## First serving trial: dispatch failure, not a fusion performance result

TP4/MTP3 run `191da44d7f45484d9cdc15fbf2722526` completed ShareGPT48/C1 at
56.1896 tokens/s, mean TTFT 549.933 ms and mean TPOT 15.563 ms. The preceding
control was 56.2861 tokens/s. All 48 texts, output lengths and speculation
statistics matched; Hermes checks passed.

Although the source and mapped library were verified on all ranks, the captured
target graph still had 2646 nodes (2558 kernels, 88 copies). The freshly compiled
rank-0 computation_graph.py contained no `strix_hc_up_mix` operation and retained
the original gate-mix operations. Thus this run does not test fused serving
performance. It must not be used to reject or promote the native fusion.

The outer Python M4 guard was unsuitable for the broad dynamic compilation
range. The correction in `hc_up_mix_dynamic.py` puts shape/layout dispatch inside
the custom operation and gives its fake implementation a dynamic leading size.
The outer condition now uses only static layer eligibility. Unsupported sizes
invoke the original GEMM and gate-mix operators.

The new test compiles at M2 with a dynamic size range, then executes M4/M3/M5/M4
through the same single Inductor graph. A test-only wrapper counts actual native
calls: one per M4 invocation, zero for the fallback sizes. Outputs must match
exactly. This closes the fixed-shape test gap; full-model dispatch still needs
verification after the corrected integration is deployed.

The dynamic-dispatch test now passes on all four nodes, including real HC
constructors, full-method Inductor checks and changed-input graph replay.
Serving counters remained unchanged during these isolated checks. The correction
has subsequently entered the full-model trial described below.

## Corrected serving trial rejected

The full trial completed at **56.3334 tokens/s**, mean TTFT 555.604 ms and
mean TPOT 15.480 ms. This is only +0.084% throughput against the preceding
56.2861 control and is not evidence of a useful speedup. More importantly,
only **14/48 generated texts match**; output lengths and speculation statistics
also differ. It generated 11810 tokens instead of 11839. Acceptance decreased
from the control trajectory; the candidate reports 52.60% and 2.58 acceptance
length. Hermes checks pass, but that does not establish arithmetic parity.

The fusion is rejected for production. The original per-node HC sources were
restored and a fresh MTP3 control is starting. Its measurements are pending.
The synthetic tests did not cover the full-model source of divergence. A future
investigation must compare actual checkpoint activations and intermediate gates
before considering another performance trial; the cause is not yet identified.

## Actual checkpoint weights, synthetic activations

After restoration and its benchmark completed, an isolated Node 4 test loaded
all 97 target HC-up BF16 matrices directly from the existing checkpoint. Twelve
input cases per matrix (independent, shared-row and positive random inputs at
scales 0.02/0.2/1/8; seed 9572) all passed: **1164 cases, zero intermediate-gate
or final-output differences**. Records include per-matrix hashes, not tensors.
Serving counters were unchanged. These are actual weights but synthetic
activations, with no full-model state or concurrent TP4 execution. They do not
explain or negate the 34 differing serving answers. Actual activation replay
or a controlled full-model path comparison is still needed to identify the cause.
