# GPU-Profiling auf der vorhandenen ROCm-Laufzeit

Torch 2.13/ROCm 10 kann in dieser Installation erfolgreiche CPU-Traces ohne ein
einziges GPU-Ereignis exportieren. Ein kleiner eigenständiger GPU-Test allein
erkennt den Fehler nicht: Er tritt nach GPU-Initialisierung im Elternprozess
und anschließendem `multiprocessing`-Spawn auf.

Der lokal nachgewiesene Diagnose-Fix lautet:

```text
ROCPROFILER_SET_ROCPROFILER_REGISTER_LIBRARY=0
```

Die Variable muss vor dem ersten Torch-Import im frischen API-/Elternprozess
gesetzt sein. Sie verhindert, dass ROCProfiler einen SDK-Pfad an die Kinder
vererbt und dadurch deren Kineto-Registrierung vorzeitig übergeht. Ein bereits
explizit gesetztes `ROCPROFILER_REGISTER_LIBRARY` wird durch das Flag nicht
gelöscht. Der vorhandene HSA-Workaround bleibt erhalten. Es sind keine
Bibliothekswechsel oder Python-Patches erforderlich.

Die Gegenprobe auf Node 4 verwendete dieselbe vLLM-Schedule mit zwei Warmup-
und 16 aktiven Iterationen: ohne Flag null GPU-Kernel, mit dem einzelnen Flag
17 GPU-Kernel und 16 GPU-Annotationen bei endlichen Rechenergebnissen. Ein
asynchroner Warmup-Nachlauf kann die zusätzliche Kernelaufzeichnung erklären.
Dieser Befund passt zum [PyTorch-Fehlerbericht #182373](https://github.com/pytorch/pytorch/issues/182373).
Das Flag ist ein Mess-Fix; ein Geschwindigkeitsgewinn folgt daraus nicht.

## Kleine Reproduktion

Die beiden Skripte `tests/smoke_torch_profiler_spawn.py` und
`tests/smoke_torch_profiler_schedule.py` müssen im Container im selben Verzeichnis
liegen. Nur bei unbeschäftigter GPU ausführen; jeder Test ist kurz begrenzt:

```bash
timeout --signal=TERM --kill-after=5s 45s \
  python3 tests/smoke_torch_profiler_spawn.py --mode vllm_scheduled
timeout --signal=TERM --kill-after=5s 45s \
  env ROCPROFILER_SET_ROCPROFILER_REGISTER_LIBRARY=0 \
  python3 tests/smoke_torch_profiler_spawn.py --mode vllm_scheduled
```

Die JSON-Ausgabe nennt echte GPU-Kernelzahlen. Ein Prozess-Exitcode allein
belegt keine vollständige GPU-Aufzeichnung; auch die absichtlich fehlerhafte
Gegenprobe beendet ihre Berechnung regulär.

## Aufzeichnung des Modells

`models/cluster.profiling.json` enthält die passende native TP4-Konfiguration
für diese vier Hosts, einschließlich des installierten QSA-Patches. Die Datei
muss unter demselben absoluten Konfigurationspfad auf allen Nodes liegen.
Die native Steuerung prüft die Übereinstimmung vor dem Neustart. Der Profiler
beginnt erst nach `/start_profile`, erfasst alle vier Ranks und stoppt nach
16 aktiven Worker-Runden. Eine Runde umfasst Target-Verifikation und Draftarbeit;
sie entspricht nicht einem Ausgabetoken.

`bench/capture_torch_profile.py` startet eine einzelne 2048-Token-Antwort und
ruft nach dem ersten Inhalt `/start_profile` auf. Im selben Verzeichnis muss
`bench_stream.py` liegen. Beispiel auf Node 1 nach erfolgreichem Neustart:

```bash
python3 bench/capture_torch_profile.py --output /tmp/profile-workload.json
```

Das Skript speichert vollständigen Text und Kontrollaufrufe und ruft am Ende
`/stop_profile` auf. Die Aufnahme ist durch Profiling verlangsamt und darf nicht
als Leistungsbenchmark verwendet werden. Die Schedule funktioniert in der
vorhandenen Laufzeit nur einmal pro frischem Worker-Profiler; ein zweiter
Start nach abgeschlossener Schedule liefert keinen verlässlichen neuen Trace.

Die rankbezogenen `.pt.trace.json.gz`-Dateien liegen im jeweils konfigurierten
Verzeichnis **innerhalb jedes Containers**. Nach dem Kopieren lassen sie sich
auf der CPU auswerten:

```bash
python3 tools/summarize_rocprof.py /pfad/zum/rank-trace \
  --format torch --output /pfad/zur/auswertung.json
python3 -m unittest discover -s tests -p test_summarize_rocprof.py -v
```

Der Parser weist CPU-only-Traces zurück. Kernel werden über Korrelationen dem
Graph-Launch zugeordnet, nicht anhand ihrer Lage innerhalb eines CPU-Zeitfensters.
GPU-Zeitstempel können wegen asynchroner Ausführung später liegen. Überlappende
Kernelzeiten sind keine additiven Wandzeiten; RCCL-Kernel enthalten Wartezeit.
Die Host-Uhren der vier Maschinen dürfen nicht ohne Synchronisationsnachweis
zu einer gemeinsamen Zeitachse zusammengefügt werden.
