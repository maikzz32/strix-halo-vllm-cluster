# CPU energy preference: no measurable benefit

All four nodes use `amd-pstate-epp`, the `powersave` governor and
`balance_performance` energy preference. The governor name alone does not
establish a CPU frequency cap. A reversible test changed only the EPP value
to `performance` on all 128 policies, then restored and verified every original
value. Governor, clock limits and power limits were unchanged.

After warming the three prompts, each phase ran six 256-token responses at C1.
All request bodies, token counts, content and reasoning matched exactly.

| Median across six fixed prompts | Before | Performance | Restored |
|---|---:|---:|---:|
| Decode tokens/s | 70.715 | 70.678 | 70.632 |
| TTFT seconds | 0.333 | 0.350 | 0.352 |

The median paired decode difference relative to the average of each prompt's
before/after controls is +0.038%. No meaningful benefit is established; keep
`balance_performance`. These short fixed-prompt rates are not the ShareGPT48
goal metric. The last full restored ShareGPT result remains 55.42 tokens/s.

A separate read-only 15-second telemetry probe sampled all four GPUs while
one 512-token answer ran. Maximum reported clocks were 2.897 GHz on each
node; maximum reported edge temperatures were 61–67 C and PPT readings
94.8–102.6 W. The reported busy interval outlasted the request, so sensor
smoothing prevents interpreting these samples as instantaneous clock ramps
or proof that throttling is absent. No GPU power setting was changed.
