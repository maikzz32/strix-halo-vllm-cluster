## 57_ple_offload_amd.py

- **Purpose:** Port `VLLM_PLE_CPU_OFFLOAD` (PLE pinned-host embedding
  offload) to the ROCm/AMD side of Qwen4Exp (Qwen3.8-Flash-Next). Upstream
  implements the offload only in `qwen4_exp/nvidia/ple_layer.py`; the AMD
  side keeps the multi-GB n-gram table device-resident. On Strix Halo
  (gfx1151) "pinned host memory" is the same unified LPDDR5 the iGPU reads,
  so the UVA gather runs at full ~256 GB/s — no PCIe hop as on a dGPU host,
  and no device-memory budget spent on the table (correct KV budgeting
  additionally needs the APU memory-reporting fix vllm#40963).
- **Mechanism:**
  1. `vllm/models/qwen4_exp/amd/ple_layer.py` — adds the Triton kernel
     `_lookup_ple_embedding_from_pinned_kernel` (verbatim from the NVIDIA
     file; platform-generic) and `Qwen4ExpPinnedHostEmbedding`: weight
     re-allocated with `pin_memory=True` on CPU, `del self.quant_method`
     to stop generic post-load GPU staging (mirrors the NVIDIA path), UVA
     view via `get_accelerator_view_from_cpu_tensor` (`is_cuda_alike`
     covers ROCm), TP-range masking through `shard_indices` in the kernel
     plus `tensor_model_parallel_all_reduce`. Includes a runtime check
     that `torch.ops._C.get_cuda_view_from_cpu_tensor` exists in the built
     `_C` — a clear error signals a HIP build gap. Prefetch runs on a
     lazily created `torch.cuda.Stream` (HIP shim). **Eager-mode
     simplification:** the NVIDIA `direct_register_custom_op` wrappers for
     start/wait prefetch are dropped — they exist only to survive
     torch.compile / CUDA-graph capture, and gfx1151 runs
     `--enforce-eager` (vllm#32180). The `qwen4_exp_amd_ple_ngram_embedding`
     custom op is kept for the `VLLM_PLE_CPU_OFFLOAD=0` path. If the
     model.py wiring is absent, forward falls back to a synchronous pinned
     lookup (correct, no overlap).
  2. `vllm/models/qwen4_exp/amd/model.py` (best effort) — wires
     `_start_layer_ple_prefetch` into the decoder-layer loop, mirroring
     the NVIDIA model, so the lookup overlaps the preceding layer.
  3. `vllm/envs.py` (only if missing) — registers `VLLM_PLE_CPU_OFFLOAD`
     in the lazy `environment_variables` dict. Both Qwen3.8 PR branches
     already carry it.
- **Gate:** `VLLM_PLE_CPU_OFFLOAD=1` (lazy envs resolution at model build
  time in the worker, after Ray applied worker env).
- **SKIP semantics (differs from fail-closed):** no
  `vllm/models/qwen4_exp/` package (stable/main builds) → SKIP, exit 0.
  qwen4_exp exists but anchors in `amd/ple_layer.py` moved → exit 42.
- **Upstream references:** vllm#53899 (model + PLE offload; build branch
  `peakcrosser7/vllm release/qwen38next_offload`, head 935728b4);
  offload source `peakcrosser7/vllm` branch `hhy/ple_offload_uva`
  (`nvidia/ple_layer.py`). All anchors verified unique against BOTH
  branches.
- **Why it is cheap here:** llama.cpp cross-check (ggml issue #27980):
  keeping the PLE table CPU-side costs ~nothing on unified memory
  (18.0 vs 18.1 tok/s). On a dGPU the same lookup crosses PCIe; on
  gfx1151 it is a same-DRAM gather at ~256 GB/s, and the prefetch stream
  overlaps it with the preceding decoder layer.
- **Status:** ported, not validated. Verified against local fixtures of
  both PR branches (apply / --check / idempotent re-apply / SKIP /
  exit-42 / WARN paths; patched files pass `py_compile` and an AST
  structure check). Must be validated on hardware with a real Qwen3.8 PR
  build: UVA view creation, Triton kernel correctness vs. the
  GPU-resident path, prefetch overlap, and weight loading into the pinned
  buffer.
- **Re-audit trigger:** exit 42 (anchors moved), the model.py WARN, the
  `_C.get_cuda_view_from_cpu_tensor` runtime error, or upstream merging an
  AMD offload path (then this patch likely conflicts → retire it).
- **Depends on (other scopes):** `patches/verify_compat.py` EXPECTED needs
  a `"57_ple_offload_amd": "vllm-src"` entry (owned elsewhere);
  `models/registry.yaml` / `scripts/serve.sh` must set
  `VLLM_PLE_CPU_OFFLOAD=1` for the qwen38 entries to activate the path.
