## 50_conch_moe_mxfp4_tune.py

- **Purpose:** Make `VLLM_GFX1X_MOE_TUNE=1` (registered in `vllm/envs.py` by
  patch 40) actually do something. The patch edits the **installed**
  `triton_kernels` package (`matmul_ogs_details/opt_flags.py`): on RDNA 3/4
  (`get_rdna_version() in (3, 4)`), skinny (`block_m < 128`) scaled
  BF16-activation x MXFP4-weight GEMMs get forced to BM=16, BN=32, BK=256
  (BK=256 is the bandwidth lever vs stock 128), `num_warps=2`,
  `num_stages=2`, and `target_kernel_kwargs={'waves_per_eu': 1, 'kpack': 1}`,
  dropping the CDNA-only `matrix_instr_nonkdim`. Each value is overridable
  via `VLLM_GFX1X_MOE_{BM,BN,BK,NW,NS,WPE}`; env is resolved lazily (Ray
  applies worker env after import). Everything else (other dtypes, archs,
  large-M tiles, opt-in unset) keeps stock behavior.
- **Target:** the installed package, not the vLLM checkout. Located via
  importlib: standalone site-packages `triton_kernels` first (runtime
  priority per `vllm/utils/import_utils.py::import_triton_kernels`), then the
  copy the ROCm vLLM wheel vendors at `vllm/third_party/triton_kernels/`
  (from ROCm/triton @ 0f380657dbf3ee86eb57558ff71df24f03b5d4e7, pinned in
  `cmake/external_projects/triton_kernels.cmake`). All anchors verified
  against that exact commit.
- **Source:** kyuz0/amd-strix-halo-vllm-toolboxes
  `scripts/patch_conch_moe_gfx1x.py` @ 614c91789e4609601e618a8d967390c04896acab
  (<https://github.com/kyuz0/amd-strix-halo-vllm-toolboxes>), adapted to the
  repo patch-layer conventions (marker `# gfx1151-patch:
  conch-moe-mxfp4-tune`, `--check`, exit 42 on moved anchors, `--src`,
  `ast.parse` fail-closed before writing).
- **Status:** verified source-side only. Anchors, scope variables
  (`block_m`, `bitwidth`, `lhs_dtype`, `rhs_dtype`, `precision_config`,
  `get_rdna_version`) and apply/idempotence/`--check`/exit-42 paths tested
  against the pinned ROCm `opt_flags.py`. **Not yet run on hardware.** The
  measured claim comes from kyuz0's Strix Halo runs (see
  `docs/VLLM_PATCH_MANIFEST.md`): 11.281 → 21.766 tok/s decode on
  DeepSeek-V4-class MXFP4 MoE; our MoE models (Qwen3.8, GLM-5.3) must be
  re-measured.
- **Ordering:** post-install only. `apply_all.sh` in the builder stage runs
  it against a tree with no installed `triton_kernels` → SKIP/defer exit 0;
  `docker/Dockerfile.fedora` re-runs it in the final stage after the wheel
  install, where it must succeed (fail-closed).
- **Re-audit triggers:** exit 42 (any of the three anchors missing/duplicated
  in `opt_flags.py`, or the patched file fails `ast.parse`), vLLM changing
  the `triton_kernels` pin or vendoring location, or no measurable
  improvement with `VLLM_GFX1X_MOE_TUNE=1` on gfx1151 MXFP4 MoE models.
