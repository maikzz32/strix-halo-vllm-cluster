## 58_glm_mtp_sparse_dispatch.py

- **Purpose:** Fix the GLM-5.3 MTP sparse-MLA dispatch on ROCm. In the PR
  #53906 tree, `ROCMAiterMLASparseImpl._forward_mla` keys its BF16
  Triton-lane selector on `num_decode_tokens == num_decodes and
  max_query_len == 1`; MTP draft steps (2+ tokens per decode request) fall
  through into gfx950-only AITER asm kernels and fault. The patch re-keys
  the selector on geometry alone (`not fp8 KV and head_size ==
  kv_lora_rank`), so MTP draft steps ride the ragged Triton kernel
  (`_rocm_sparse_attn_prefill_ragged_triton` handles per-query indptr
  natively). It also ORs the selector with the env knob
  `VLLM_GFX1X_FORCE_TRITON_SPARSE=1` (lazy per-call read): on gfx1151 all
  asm/Gluon AITER lanes are unreachable anyway, so the Triton lane must
  stay force-selectable even if upstream adds new heuristics.
- **Target:** `vllm/v1/attention/backends/mla/rocm_aiter_mla_sparse.py`
  (primary guess), else any file defining `ROCMAiterMLASparseImpl` +
  `_forward_mla` (content search).
- **Upstream reference:** vllm#53943
  (<https://github.com/vllm-project/vllm/issues/53943> — an OPEN issue, not
  a merged fix; same fixes in ZJY0516/vllm#5 and #7) on top of PR #53906
  (<https://github.com/vllm-project/vllm/pull/53906>). Measured on gfx950
  TP=8: 2632 → 3760 tok/s @ N=64.
- **Status:** re-audited against vLLM v0.28.0: no `glm5_next` package and
  no shape-keyed selector upstream (issue still OPEN), so the patch SKIPs
  there — verified. The `glm5_present` check now runs BEFORE the anchor
  check (previously `find_target` matched the upstream class and the patch
  42'd on every stable build). Selector expression/force-knob polarity
  **still unconfirmed against a real glm-release checkout**. The exact selector expression (variable names for
  the fp8-KV flag and `kv_lora_rank`) and the polarity of the force-knob
  (assumes selector-true = Triton lane) must be confirmed on the first GLM
  build. The patched file is re-parsed with `ast.parse` before writing, so
  a layout mismatch fails closed instead of corrupting the tree.
- **SKIP semantics:** no `glm5_next`/`Glm5Next` package in the tree (e.g. a
  build off vLLM main without PR #53906) → SKIP with a note, exit 0.
  GLM-5.3 present but class/anchors missing → exit 42.
- **Re-audit trigger:** exit 42 (anchor `num_decode_tokens == num_decodes`
  gone, `max_query_len == 1` missing from the selector statement, no
  geometry terms in it, or the patched file no longer parses), the
  leftover-selector WARN, or MTP still faulting/underperforming on the GLM
  build after the patch landed.
- **Date:** 2026-08-30.
