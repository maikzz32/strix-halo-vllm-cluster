## 58_glm_mtp_sparse_dispatch.py

- **Purpose:** Fix the GLM-5.3 MTP sparse-MLA dispatch on ROCm. In the PR
  #53906 tree the BF16 Triton-lane selector is the module-level helper
  `_use_rocm_sparse_triton` in
  `vllm/v1/attention/backends/mla/rocm_aiter_mla_sparse.py`, which ANDs the
  geometry terms (`not fp8 KV`, `head_size == kv_lora_rank`) with two shape
  terms (`plain_decode = num_decode_tokens == num_decodes`, and
  `num_prefills > 0 or (num_decodes > 0 and max_query_len == 1)`). MTP draft
  steps (2+ tokens per decode request) fail both shape terms, fall through
  into gfx950-only AITER asm kernels and fault. The patch re-keys the
  selector on geometry alone, so MTP draft steps ride the ragged Triton
  kernel (`_rocm_sparse_attn_prefill_ragged_triton` handles per-query indptr
  natively). It also ORs the selector with the env knob
  `VLLM_GFX1X_FORCE_TRITON_SPARSE=1` (lazy per-call read): on gfx1151 all
  asm/Gluon AITER lanes are unreachable anyway, so the Triton lane must
  stay force-selectable even if upstream adds new heuristics.
- **Target:** `vllm/v1/attention/backends/mla/rocm_aiter_mla_sparse.py`
  (primary), else any file defining `ROCMAiterMLASparseImpl` +
  `_forward_mla` (content search). The helper is called from the metadata
  builder (gates the persistent AITER work-metadata build) and from
  `_forward_mla` — selector-true calls `rocm_sparse_attn_prefill` with
  ragged indices — so re-keying the helper fixes both call sites
  consistently; the helper keeps its (now unused) shape parameters, so the
  call sites stay untouched.
- **Upstream reference:** vllm#53943
  (<https://github.com/vllm-project/vllm/issues/53943> — an OPEN issue, not
  a merged fix; related ROCm enablement work in ZJY0516/vllm#5 and #7) on
  top of PR #53906 (<https://github.com/vllm-project/vllm/pull/53906>).
  Measured on gfx950 TP=8: 2632 → 3760 tok/s @ N=64.
- **Status:** re-audited against the real glm-release checkout @ 36bb3795
  (PR #53906 head, 2026-08-31). The previously hypothesized inline selector
  in `_forward_mla` does not exist there; the confirmed form is the
  module-level `_use_rocm_sparse_triton` helper with the `plain_decode`
  indirection, and the selector-true = Triton-lane polarity is confirmed by
  both call sites. The anchors are now verbatim (`SELECTOR_OLD`) against
  that tree; the old regex statement-machinery was dropped. Upstream
  main/stable (incl. v0.28.0) has no `glm5_next` package → SKIP, verified
  by the regression run. The patched file is re-parsed with `ast.parse`
  before writing, so a layout mismatch fails closed instead of corrupting
  the tree.
- **SKIP semantics:** no `glm5_next`/`Glm5Next` package in the tree (e.g. a
  build off vLLM main without PR #53906) → SKIP with a note, exit 0.
  GLM-5.3 present but class/anchors missing → exit 42.
- **Re-audit trigger:** exit 42 (verbatim selector anchor or
  `def _use_rocm_sparse_triton(` not matched exactly once, target class
  absent, or the patched file no longer parses), the leftover-shape-term
  WARN, or MTP still faulting/underperforming on the GLM build after the
  patch landed.
