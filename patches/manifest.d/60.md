## 60_skinny_gemm_m1.py

- **Purpose:** fast path for the m=1 skinny GEMM that dominates batch-1
  decode on gfx1151. Per vllm#52631, `rocm_unquantized_gemm_impl`
  (`vllm/model_executor/layers/utils.py`) dispatches m > 8 to wvSplitK
  and m % 4 == 0 to LLMM1, so m == 1 falls through to
  `F.linear` -> rocBLAS, which selects a pathological
  `Cijk_..._MT128x32x16_GSU1` kernel (one workgroup walking k=2048).
  The shape is `shared_expert_gate` [1, 2048] — once per layer per
  token on Qwen2/3.5-MoE models (`bias=False`, so the bias arm is
  defensive only).
- **Measured (vllm#52631, gfx1151, ROCm 7.14, vLLM 0.27.1,
  Qwen3.5-MoE 35B-A3B, batch-1 decode):** 137.5 us/call x 40
  calls/step = 5.48 ms of a 40.06 ms step (13.7%). The fix measures
  6.82 us/call (20.5x; standalone reproducer 139.93 -> 6.82 us) and
  improved decode 40.06 -> 34.79 ms/step, 24.53 -> 28.32 tok/s
  (+15.5%). The Cijk kernel disappears from the profile entirely and
  wvSplitK is untouched.
- **Fix:** inserts an `elif m == 1 and on_gfx1x():` branch between the
  wvSplitK and LLMM1 branches of the skinny ladder, computing
  `(x_view * weight.reshape(-1)).sum(-1, keepdim=True)` (the issue's
  proposed fix). The branch sits inside `if use_skinny:` (already
  gated on fp16/bf16, contiguous operands, gfx9/gfx1x); the extra
  `on_gfx1x()` narrows it to RDNA only — gfx9/MI300 and all non-ROCm
  behavior is untouched.
- **Numeric caveat:** bf16 * bf16 rounds each of the K element
  products to bf16 before the fp32 sum, so output is NOT bitwise
  identical to `F.linear` — max abs diff 3.1e-02..2.5e-1 at K=2048 on
  dot products of order ~45 (per the issue). This is the bf16
  accumulation-order noise class that shape-based kernel selection
  already accepts, but correctness MUST be validated with an
  output-parity check on hardware (greedy-decode A/B against
  `VLLM_GFX1X_SKINNY_M1=0`; the issue reporter saw 794/1028 identical
  greedy characters before a near-tie divergence and zero malformed
  tool calls in 400 problems — healthy, but not a controlled A/B).
- **Activation:** on by default; `VLLM_GFX1X_SKINNY_M1=0` restores the
  stock rocBLAS fallback. Lazy env resolution inside the impl (Ray
  applies worker env after import), like the other `VLLM_GFX1X_*`
  knobs.
- **Upstream status (2026-08-30):** issue open; vllm#53283 (open,
  unmerged) instead widens the wvSplitK guard to
  `(m == 1 or m > 8) and 0 < n <= 5` — bitwise-cleaner (BF16 matched
  `F.linear` exactly in their sweep; +12.79% decode measured on
  gfx1151). The patch detects both that guard form and any
  `elif m == 1` branch and SKIPs cleanly instead of double-patching.
  If #53283 merges, prefer upstream and drop this patch.
- **Anchor:** the two-line junction `return out.reshape(...) /
  elif m % 4 == 0 and n == 1 and k <= 8192 and bias is None:` in the
  skinny ladder — verified identical on vLLM main and on dev tag
  v0.28.1rc0 (79651d6) as of 2026-08-30, so no drift expected between
  our pinned refs and main. `ast.parse` fail-closed before writing.
- **Re-audit triggers:** exit 42 (ladder anchor gone/duplicated,
  `utils.py` moved, patched file fails `ast.parse`), or vllm#53283 /
  any upstream m==1 dispatch landing (then this patch is obsolete and
  self-skips).
- **Validate on hardware:** (1) torch-profiler decode run — the
  `Cijk_..._GSU1` kernel gone, ~5.5 ms/step reclaimed; (2) tok/s A/B
  vs `VLLM_GFX1X_SKINNY_M1=0` (expect ~+15% batch-1 decode on
  Qwen3.5-MoE 35B-A3B); (3) greedy output-parity check patched vs
  unpatched (numeric caveat above); (4) CUDA-graph capture on (the
  mul+sum is capture-safe; the issue confirmed the pathology is not a
  graph artifact).
