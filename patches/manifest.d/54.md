## 54_aiter_rdna_enable.py

- **Purpose:** Make AITER's **Triton** kernels usable on gfx1151 while
  keeping CK/ASM kernels off (CDNA-only dead ends). Blueprint: the gfx1100
  RDNA enablement (research notes cite aiter#4604; that PR number does not
  resolve on ROCm/aiter — in current vLLM the same pattern landed as the
  RDNA4/gfx12 functions in `vllm/_aiter_ops.py`, which this patch mirrors).
  Does NOT flip the master switch: `VLLM_ROCM_USE_AITER=0` semantics stay
  intact (patch 40 force-disables it on gfx1x); enablement is gated on the
  separate `VLLM_GFX1X_AITER_TRITON=1` knob, resolved lazily.
- **Steps:**
  - **A. `vllm/_aiter_ops.py`** (source checkout via `--src`, or the
    installed package in site-packages): adds
    `is_aiter_found_and_supported_on_gfx1151()` (analog of the RDNA4 gate)
    and extends `rocm_aiter_ops.is_rdna_aiter_enabled()` so the Triton-only
    subpaths (`is_rdna_linear_enabled`, GDN Triton kernels) activate on
    gfx1151 when the knob is on.
  - **B. installed aiter `aiter/ops/triton/utils/_triton/arch_info.py`**
    (older layout: `aiter/ops/triton/utils/arch_info.py`): adds gfx1151/
    gfx1150 to `_LDS_CAP_BYTES` (conservative 64 KiB per-CU budget; RDNA 3.5
    exposes 128 KiB LDS per WGP) — without it every AITER Triton kernel
    budgeting LDS dies with KeyError. The `_ARCH_TO_DEVICE` dict from the
    research notes does **not** exist in aiter v0.1.19 or main; if it
    appears, the patch exits 42 for re-audit instead of guessing.
  - **C. installed aiter `csrc/cpp_itfs/utils.py`:** ensures gfx1151 is in
    the `validate_and_update_archs()` allow-list (already present in aiter
    v0.1.19 → SKIP there).
  - **D. installs `patches/vendor/vec_convert.h`** over
    `aiter_meta/csrc/include/ck_tile/vec_convert.h` (vendored from kyuz0's
    `patch_aiter_headers.py`): RDNA scalar fallbacks for CDNA-only packed
    conversion ISA (`v_pk_mul_f32`, `v_cvt_pk_fp8_f32`, `v_cvt_pk_bf8_f32`).
- **CRITICAL correctness note:** the vendored `vec_convert.h` makes FP4
  conversions return ZERO tensors off-gfx950 — any AITER FP4 path reached
  on gfx1151 is silently wrong. The patch keeps FP4 gated off (never touches
  `is_fp4_avail()`, asserts post-patch that it does not cover gfx1151).
- **Invocation:** run by `apply_all.sh` in the builder stage applies step A
  only (aiter is not installed there; steps B–D print a WARN and defer).
  The Dockerfile's final stage must re-run it after wheel installation:
  `python3 /opt/patches/54_aiter_rdna_enable.py --src /opt/src/vllm
  --site-packages "$(python3 -c 'import site; print(site.getsitepackages()[0])')"`.
  (`--site-packages` optional; falls back to importlib detection. This is
  the same post-install mechanism patch 50 uses.)
- **Status:** expected-to-need-adjustment. Anchors verified against vLLM
  dev tag v0.28.1rc0 and aiter v0.1.19 (`AITER_REF` in
  docker/Dockerfile.fedora).
- **Re-audit trigger:** exit 42 (`_aiter_ops.py` anchors gone, arch_info.py
  missing/`_ARCH_TO_DEVICE` appears, `aiter_meta` header layout changed).
- **Validate on hardware:** with `VLLM_GFX1X_AITER_TRITON=1`, confirm AITER
  Triton blockscale/linear paths actually pass numerics on gfx1151, that no
  CK/ASM op is ever dispatched, and that FP4 paths stay unreachable.
- **Date:** 2026-08-30.
